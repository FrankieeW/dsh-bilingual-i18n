# 开发记录：dsh-bilingual-i18n（DSH 中英双语界面 + 英文占比滑块）

记录「为什么这么做」和踩过的坑。代码结构与不变量见 [AGENTS.md](../AGENTS.md)，
用户向用法见 [README.md](../README.md)，DSH 机制的源码级笔记见 [DSH客户端机制调研.md](./DSH客户端机制调研.md)。

---

## 1. 需求

在 DSH 会话里一路提出来的（2026-10-21，原话存在 `~/.dsh/sessions` 的会话日志里）：

1. 「我想一个中英双语的 i18n」
2. 「加个滑块吧 最左边是 bilingual 最右边是纯英语 你帮我设计为 5 档」

后来把它叫作 **英语占比滑块**：从左到右，英文的占比一路增加。

## 2. 第一版（v0.1，DSH 自带 agent 写的）为什么被打回

| 问题 | 后果 |
|---|---|
| 5 档 = 双语 → 英文在前 → 「英文 ≤ 8 字符才保留」→ 「只保留术语」→ 纯英文 | 第 3、4 档的英文**比第 1 档还少**，到第 5 档才突然 100%——根本不是「英文占比」 |
| 每档注册一门语言 | 语言下拉多出 4 个看不懂的项 |
| 注册不交 disposer、合成结果「只做一次」 | 插件重载报「已注册」；之后才变的词典永远不更新 |
| 中英文无脑拼接 | `time.locale` 变成 `zh-CN en`（传给 `Intl` 直接报错）、文档 URL 变成两段、`、 , `、`3分 m`、Markdown 标题不在行首 |
| 「占位符去重」把英文那半的 `{name}` 删了 | 运行时本来就会替换全部同名占位符，去重反而少字 |
| README 写了 `localStorage` 切语序 | 代码里根本没读这个键 |
| 设置行粗糙 | 原生 range + 内联样式，标题加粗、没分隔线，和相邻行不是一个风格；中文界面下还标着「最左」 |
| 从没在真实界面里验证过 | 以上问题都是一打开就能看见的 |

## 3. 标定：5 档怎么分

从 `app.asar` 里把全部内置客户端插件跑起来，收集真实注册的 zh / en 词典（`scripts/calibrate.mjs` 就是这套流程）：
DSH 0.2.1-rc.2 共 60 个命名空间、约 2700 条中英不同的文案。按**英文词数**（不计占位符）统计：

| 英文词数 | 占比 | 累计 |
|---|---|---|
| ≤ 1 | ≈ 30% | 30% |
| 2 | ≈ 27% | 57% |
| 3–5 | ≈ 24% | 81% |
| ≥ 6 | ≈ 19% | 100% |

于是阈值取 1 / 2 / 5：第 2–4 档纯英文占比 ≈ 30% / 57% / 81%，间隔均匀、严格递增。
按词数而不是字符数，是因为「先换掉简单的词、长句保留中文对照最久」符合学英文的直觉，也好跟用户解释
（每档的名字就是「单词 / 短语 / 短句」）。

滑块下方显示的是**运行时现算**的占比（随装的插件变化），不是写死的数字。

## 4. 设计

### 4.1 一门语言 + Proxy 词典

- 第 1–4 档共用语言 `zh-en`（沿用旧版第 1 档的 id）；第 5 档就是内置 `en`。语言下拉只多一项。
- 每个同时有 zh / en 的命名空间注册一个 Proxy：取词时读实时档位现算，带缓存。
  切档时只需「重注册一个命名空间」让运行时推进 revision，已渲染的界面就会重新取词。
- 订阅运行时变化，之后注册的命名空间自动纳入；zh 或 en 被撤销时跟着撤销。
- fallback 设为 `zh`：只有中文的插件词典显示中文而不是键名。

### 4.2 原子条目

约 5% 的条目不是给人看的整句，而是值或零件：语言代码、URL、分隔符、单位、首尾带空格的句子片段、
`{n}min` 这类缩写模板、键名就写着 prefix/suffix 的前后缀……这些只能二选一：第 1 档取中文，
到其词数对应的档位整体换英文。判断规则在 `isAtomic()`，误伤用 `npm run calibrate -- --atomic` 检查。

### 4.3 偏好存在哪

`level`（1–4）和 `order` 由宿主半侧声明成 volatile Config，经 `ctx.configForms` 写进 profile 的
`cordis.patch.yml`，和其它「通用」设置一样跨浏览器生效；`localStorage` 留一份副本保证启动即用。
schemastery 走可选 peer：运行时提供，取不到就不声明 Config，退回本地副本。

### 4.4 设置行

照 DSH 自己的设置行写：14px 常规字重标题、12px tertiary 描述、16px 上下内边距、0.5px 分隔线；
填充色用 `--dsw-alias-brand-primary`（浅色黑、深色白，和 Switch 一致）。
5 个刻度下标名字和**该档实测的纯英文占比**；中英并列时右上角可切语序（DSH 的 SegmentedControl）；
当前是中文时滑块不落档，并写明当前语言。原生 range 负责键盘、读屏和拖动。

## 5. 只有在真实界面里才发现的三个坑

单测和集成测试全绿之后，用隔离的 `dsh web` + 无头 Chrome 真拖了一遍，又挖出三个：

1. **快速拖动停错一档。** 从第 4 档快速拖到第 1 档再拖回第 4 档，最后停在第 3 档。
   原因：`onChange` 来自几帧前的渲染，闭包里的 `position` 还是 4，「拖回 4」被当成没变化丢掉了。
   修法：组件不再去重，去重挪到 `selectLevel`，看 `locale.getSnapshot()` 的实时状态。
2. **松手后滑块跳回中间档。** 拖动时每一档都写一次 Host；设置镜像随后陆续推来这些排队写入的中间值，
   被当成「别处改了设置」采用了。修法：每个字段同时只有一次写入在路上，期间只记最新值、写完补写；
   写完之前不采用 Host 推来的该字段值。一次拖动最多写两次。
3. **在第 4、5 档之间来回拖，松手后界面闪回中英。** 第 5 档是 `setLocale('en')`，来回拖会连发
   `locale.preference` 写入；DSH 自己的 LocaleRuntime 会采用设置镜像推来的旧偏好，界面闪一下。
   修法：在 `zh-en` 里先「预览」第 5 档（Proxy 全部返回英文），停稳 400ms 再真正切到 `en`；
   离开第 5 档、改选别的语言或插件卸载都会取消。

三个都写成了回归测试（`test/run-tests.mjs` 的 [2][3][5] 组）和端到端检查（`scripts/e2e.mjs`）。

## 6. 验证

- `npm test`：98 项。最重的一组把真实 locale 运行时和全部内置插件词典搭起来，逐档核对每一条取词结果
  与规则一致、占位符不丢、语言代码与 URL 每档都合法、之后注册的命名空间自动纳入、卸载不留注册、
  重复加载不报错。
- 变异检查：分别去掉「切档重渲染」「fallback = zh」「原子条目」「in-flight 不采用」，对应用例都会失败。
- `npm run e2e`：11 项，在真实界面里走完中文 → 各档 → 语序 → 语言下拉 → 重载 → 快速拖动 → 4/5 档来回拖。

## 7. 已知限制 / 以后可以做

- 由几个词条拼出来的句子（自动化任务的「每周一、三 09:00」等）在并列档位里会中英混杂：
  被填进去的词本身也按档位合成。要根治得在 `translate` 层拿到参数的来源，词典层做不到。
- 插件市场的插件标题 / 简介走 `resolveText`，不经词典，中英双语下显示中文。
- 注册时就取好文案、不走插槽渲染的地方（DSH 自身限制），切档后要刷新页面。
- `ctx.locale.dicts` 是内部字段；DSH 改名时插件会提示不可用。
